# ASTRIS v0.1.20 — Globe Camera + GPU Buffer Stability\n\n## Мета\n\nЗакрити три пов'язані runtime-симптоми:\n\n```text\nperformance warning: READ-usage buffer was written...\nEasing around a point is not supported under globe projection.\nWebGL: too many errors, no more errors will be reported...\n```\n\n## Що виявлено\n\n1. `Easing around a point...` з'являється тільки коли globe-camera отримує `easeTo()` з полем `around`. Для globe це прямо позначено MapLibre як unsupported path.\n2. ASTRIS custom orbital layer на кожному render frame синхронно читав багато GL state через `gl.getParameter()` і після рендера повторно прив'язував VAO/program/buffer, які належать MapLibre. Це створювало зайві CPU↔GPU sync points і ризик відновлення вже неактуального GL state.\n3. Динамічна orbital geometry переписувала той самий VBO через `bufferData(..., DYNAMIC_DRAW)`. Chromium warning описує саме сценарій, коли READ-usage buffer після fence знову переписується до завершення readback shadow-copy lifecycle.\n4. У MapLibre є окремий upstream issue із тим самим Chromium warning, тому ASTRIS не маскує повідомлення через `console.*` interception.\n\n## Реалізовано\n\n### Globe camera guard\n\n- `aroundCenter: false`;\n- `scrollZoom`, `touchZoomRotate`, `touchPitch` у globe працюють від центра;\n- double-click zoom у globe вимкнений;\n- `map.easeTo()` захищено wrapper-ом, який у globe видаляє `around` перед передачею в MapLibre.\n\n### WebGL context\n\n```text\nantialias: false\npreserveDrawingBuffer: false\npowerPreference: high-performance\n```\n\nASTRIS orbital point sprites мають власний shader edge/glow, тому MSAA не є обов'язковим для їх вигляду.\n\n### GPU VBO ring\n\nБуло:\n\n```text\n1 VBO\n→ draw\n→ fence/readback lifecycle\n→ rewrite same VBO\n```\n\nСтало:\n\n```text\nVBO0 → VBO1 → VBO2 → VBO3 → ...\n```\n\nКожний geometry stream має 4 GPU slots. Пам'ять збільшується тільки коли потрібна більша capacity, після чого дані оновлюються через `bufferSubData`. Usage hint — `STREAM_DRAW`.\n\n### Custom-layer state\n\nВидалено render-frame `gl.getParameter()` для:\n\n- depth mask;\n- depth func;\n- blend factors;\n- current program;\n- VAO;\n- ARRAY_BUFFER binding.\n\nCustom shader output переведений на premultiplied alpha, що відповідає documented MapLibre custom-layer blend contract.\n\n### Repaint budget\n\nПрибрано redundant `triggerRepaint()`:\n\n- під час `move`, де MapLibre і так уже рендерить кадри;\n- після `updateClock()`, який сам викликає repaint.\n\n## Важлива межа виправлення\n\n`READ-usage buffer` не оголошується гарантовано усуненим на рівні Chromium/MapLibre, оскільки ідентичний warning відтворюється upstream у MapLibre без ASTRIS. v0.1.20 прибирає ASTRIS-side buffer/state churn, який міг множити цей warning і супутні GL errors.\n\n## Acceptance\n\nПеревірити у Chrome/Edge:\n\n1. 5 хвилин idle globe;\n2. 3 хвилини wheel zoom;\n3. 3 хвилини left-drag;\n4. 3 хвилини rotate/pitch;\n5. перемикання Globe ↔ Mercator 20 разів;\n6. labels/grid/buildings/terrain ON/OFF;\n7. GNSS + Starlink.\n\nОчікується:\n\n```text\nEasing around a point...           0\nASTRIS JS exceptions               0\nMapLibre label expression errors   0\nWebGL too many errors              0\n```\n\nЯкщо Chromium READ-usage warning залишиться одиничним/періодичним без GL errors і без деградації FPS, це вважається upstream browser/MapLibre diagnostic, а не ASTRIS runtime failure.\n
